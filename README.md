# nexus-commerce

فريق من 5 وكلاء ذكاء اصطناعي متساوين (A1 إلى A5، بلا قائد) يدير متجر دروبشيبينغ
على Shopify بالاعتماد على CJ Dropshipping كمورّد وحيد. كل فعل له أثر خارجي
(نشر منتج، تغيير سعر، طلب من المورّد، تحديث تتبع) يمر أولاً بإجماع الخمسة، ثم
بموافقتك على Telegram، قبل أي تنفيذ حقيقي.

المشروع يعمل افتراضياً بوضع `DRY_RUN=true`: لا شراء حقيقي، لا نشر حقيقي، لا
رسائل حقيقية للزبائن — كل شيء يُسجَّل فقط في قاعدة بيانات SQLite محلية
(`nexus_commerce.db`) مع سجل تدقيق كامل لكل قرار.

## خطوات الإعداد بالترتيب

### 1. المتطلبات

- Python 3.12 (أو Docker، القسم أدناه).
- حساب Shopify له Access Token من نوع Admin API.
- حساب CJ Dropshipping (المفاتيح تُحفظ، لكن التنفيذ الحقيقي ضدها غير جاهز بعد
  — انظر "ما ينقص" في `docs/UNVERIFIED.md` وفي التقرير النهائي).
- بوت Telegram (عبر [@BotFather](https://t.me/BotFather)) — هذا الجزء جاهز
  ويعمل حقيقياً بدون أي نقص.
- مفتاح Anthropic API (`ANTHROPIC_API_KEY`) — هذا ما يفكر به الوكلاء الخمسة
  فعلياً، وهو الجزء الوحيد الذي **يستدعي API خارجياً حقيقياً حتى في DRY_RUN**،
  لأن اتخاذ القرار نفسه ليس من "الأفعال ذات الأثر الخارجي" التي يوقفها DRY_RUN.

### 2. التثبيت المحلي (بدون Docker)

```bash
cd nexus-commerce
python3.12 -m venv .venv
.venv/bin/pip install -r requirements.txt
cp .env.example .env
```

افتح `.env` وعبّئ ما تملكه من مفاتيح (اتركه فارغاً لأي خدمة لا تملك مفتاحها
الآن — المشروع يستخدم نسخة محاكاة (mock) تلقائياً لتلك الخدمة بدل أن يفشل).

### 3. الحصول على TELEGRAM_CHAT_ID

1. أنشئ بوتاً عبر `@BotFather` واحصل على `TELEGRAM_BOT_TOKEN`.
2. أرسل أي رسالة للبوت من حسابك أنت (يجب أن تبدأ المحادثة أنت أولاً).
3. افتح `https://api.telegram.org/bot<TOKEN>/getUpdates` في المتصفح وابحث عن
   `"chat":{"id": ...}` — هذا هو `TELEGRAM_CHAT_ID`.

### 4. تشغيل الاختبارات (يجب أن تنجح كلها قبل أي شيء آخر)

```bash
.venv/bin/python -m pytest -v
```

النتيجة الفعلية الحالية لهذا التشغيل: **68 اختباراً، كلها ناجحة (68 passed)**
— التفاصيل الكاملة والأرقام في `docs/FINAL_REPORT.md`.

### 5. التشغيل محلياً

```bash
.venv/bin/python -m src.main
```

- إن كان `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID` مضبوطين: يبدأ الاستماع
  الحقيقي لأزرار "موافق"/"رفض" على Telegram فوراً.
- إن لم يكونا مضبوطين: المقترحات التي تصل لمرحلة الإجماع تبقى بحالة
  `awaiting_telegram` منتظرة إلى أن تضبط المفتاحين.
- الحلقة الرئيسية (APScheduler) تعمل في الخلفية: كل `HOURLY_INTERVAL_MINUTES`
  دقيقة (الطلبات المدفوعة ← التتبع ← مراجعة الأسعار)، ومرة كل منتصف ليل
  (اقتراح منتجات جديدة).

### 6. التشغيل عبر Docker (للسيرفر)

```bash
docker compose up -d --build
```

يقرأ `docker-compose.yml` ملف `.env` تلقائياً، ويحفظ قاعدة البيانات في جزء
(volume) دائم باسم `nexus_commerce_data` حتى لا تُفقد بين عمليات إعادة
التشغيل.

## كيف تنتقل من DRY_RUN إلى التشغيل الحقيقي

**هذا القسم الأهم قبل أي صرف حقيقي.** اقرأه كاملاً قبل تغيير `DRY_RUN`.

### أولاً: ما هو جاهز للتشغيل الحقيقي الآن

- **Anthropic (تفكير الوكلاء الخمسة)**: جاهز تماماً، يعمل منذ اليوم الأول
  حتى داخل DRY_RUN.
- **Telegram (موافقتك/رفضك)**: جاهز تماماً، يعمل منذ اليوم الأول حتى داخل
  DRY_RUN — لأن إرسال رسالة الموافقة لك شخصياً ليس "أثراً خارجياً" يوقفه
  DRY_RUN، بل هو نفسه آلية الموافقة.

### ثانياً: ما هو **غير جاهز** وسيرفض العمل برسالة خطأ واضحة لو ضبطت `DRY_RUN=false`

- **Shopify**: الاتصال والمصادقة (session) جاهزان ومُتحقَّق منهما حقيقياً،
  لكن كل عملية فعلية (قراءة الطلبات، إنشاء منتج، تعديل سعر، تحديث تتبع) ترفع
  `NotImplementedError` لأن نص استعلامات GraphQL الفعلي (أسماء الحقول
  والطفرات/mutations) لم يُتحقَّق منه — `shopify.dev` كان محجوباً عن هذه
  الجلسة. التفاصيل الكاملة في `docs/UNVERIFIED.md`.
- **CJ Dropshipping**: كل الواجهة البرمجية (الـ API) غير مُتحقَّق منها بالكامل
  — لا الرابط الأساسي، ولا طريقة المصادقة، ولا أي endpoint. كل دالة في
  `RealCJClient` ترفع `NotImplementedError`. `developers.cjdropshipping.com`
  كان محجوباً، ولم يوجد أي مصدر رسمي بديل يمكن الوصول إليه.

هذا ليس نقصاً عشوائياً — هو تطبيق حرفي لقاعدتك الخاصة: **"إن لم تستطع التحقق
من شيء، اكتبه في UNVERIFIED.md ولا تستخدمه"**. لم يُخترع أي اسم حقل أو
endpoint من الذاكرة في هذا المشروع.

### ثالثاً: خطوات الانتقال الفعلية، بالترتيب

1. **عبّئ كل المفاتيح في `.env`**: `ANTHROPIC_API_KEY`، `SHOPIFY_SHOP_URL`،
   `SHOPIFY_ACCESS_TOKEN`، `CJ_API_KEY`، `CJ_API_BASE_URL`،
   `TELEGRAM_BOT_TOKEN`، `TELEGRAM_CHAT_ID`.
2. **اضبط حدود الصرف بعناية**: `MAX_ORDER_COST`، `DAILY_SPEND_LIMIT`،
   `MIN_MARGIN` — هذه هي خط الدفاع الأول قبل أن يصل أي مقترح حتى إلى الوكلاء
   الخمسة.
3. **أكمل `src/integrations/shopify_client.py`**: استبدل كل
   `NotImplementedError` في `RealShopifyClient` باستعلامات/طفرات GraphQL
   حقيقية، بعد التحقق منها من `shopify.dev` مباشرة (الآن متاح لك، لم يكن
   متاحاً لهذه الجلسة) أو من توثيق Shopify الرسمي. سجّل كل مصدر في
   `docs/SOURCES.md` بنفس الأسلوب المستخدم في بقية الملف.
4. **أكمل `src/integrations/cj_client.py`**: نفس الشيء، لكن من توثيق CJ
   Dropshipping الرسمي لحسابك (قد يختلف شكل الـ API بين حسابات/إصدارات CJ،
   فتحقق من حسابك أنت تحديداً).
5. **شغّل الاختبارات كاملة من جديد** (`pytest -v`) — يجب أن تبقى كلها ناجحة
   بعد أي تعديل.
6. **اختبر بـ `DRY_RUN=true` أولاً** ضد حسابك الحقيقي (Shopify/CJ حقيقيان،
   لكن بلا تنفيذ فعلي) وراقب سجل التدقيق (`audit_log` في قاعدة البيانات)
   وتأكد أن القراءات (الطلبات، الأسعار) صحيحة.
7. **فقط بعد كل ما سبق**: غيّر `DRY_RUN=false` في `.env` وأعد تشغيل الخدمة.
   من هذه اللحظة، أي مقترح يصل لإجماع الخمسة ثم موافقتك على Telegram **سيُنفَّذ
   حقيقياً**: نشر منتج حقيقي، تغيير سعر حقيقي، طلب حقيقي من CJ بأموال حقيقية.

### رابعاً: احتياطات لا يجب تجاوزها أبداً

- طلب المنتج من CJ لا يحدث إلا بعد أن يكون `financial_status` للطلب في
  Shopify هو `paid` بالفعل — هذا مفروض في الكود نفسه
  (`src/tools/limits.py::check_payment_confirmed`)، وليس مجرد اتفاق شفهي.
- أي مقترح شراء يتجاوز `MAX_ORDER_COST` أو يدفع إجمالي اليوم فوق
  `DAILY_SPEND_LIMIT` يُرفض تلقائياً قبل أن يراه أي وكيل — راجع
  `src/tools/limits.py`.
- لا تحذف أو تُقلّل سجل `audit_log` — هو الدليل الوحيد القابل للمراجعة على كل
  قرار اتُّخذ ومن وافق عليه ومتى.

## هيكل المشروع (مرجع سريع)

```
src/
  agents/        وكيل واحد (A1..A5)، بروتوكول الإجماع، مراجعة ما بعد التنفيذ
  db/            المخطط، الموديلات، كل استعلامات SQL
  integrations/  Anthropic / Shopify / CJ / Telegram — كل واحدة: واجهة + حقيقية + mock
  tools/         حاسبة الربح، حدود الصرف، أداة بحث الويب
  workflows/     الأنابيب الأربعة (طلبات/تتبع/أسعار/منتجات جديدة) + منفّذ + pipeline عام
  app.py         نقطة اختيار حقيقي-أو-mock لكل خدمة بحسب ما هو مضبوط في .env
  scheduler.py   وظائف APScheduler الساعية واليومية
  main.py        نقطة التشغيل الدائمة (الخدمة)
tests/           68 اختباراً، منها محاكاة end-to-end كاملة بوضع DRY_RUN
docs/
  SOURCES.md     كل مصدر توثيق رسمي استُخدم فعلياً، مع الرابط
  UNVERIFIED.md  كل ما لم يُتحقَّق منه ولم يُستخدم
  FINAL_REPORT.md التقرير النهائي: ماذا بُني، نتائج الاختبارات الفعلية، الناقص
```
