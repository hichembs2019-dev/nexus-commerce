# nexus-commerce

وكيل ذكاء اصطناعي واحد يدير متجر دروبشيبينغ على Shopify بالاعتماد على CJ
Dropshipping كمورّد وحيد، **بلا أي بوابة موافقة قبل التنفيذ** - لا تصويت
وكلاء، لا تليجرام. مقترح يجتاز فحصاً رياضياً صارماً واحداً فقط (هامش ربح
حقيقي أكبر من صفر) يُنفَّذ تلقائياً وفوراً.

**لا تصويت موافق/رافض/معدِّل إطلاقاً (قرار صريح من المالك، 2026-10-18):**
"مافيش موافق رافض معدل، فيه شغل و بس... مافيش رفض و موافقة" - بعد أن
أثبتت الأرقام الحقيقية من قاعدة البيانات أن 34 من 38 مقترح نشر منتج فشل
في الوصول لإجماع الوكلاء، وصفر بيع حقيقي تحقق قط. الآن `submit_proposal()`
(`src/workflows/pipeline.py`) لا يستدعي أي وكيل للموافقة إطلاقاً - الفحص
الوحيد المتبقي هو `_check_limits()`، رياضيات صرفة (هل الربح الحقيقي أكبر
من صفر)، وليس رأياً من ذكاء اصطناعي. آلية التصويت القديمة
(`agents/consensus.py`) ما زالت موجودة ومُختبرة لكنها **غير مستدعاة من أي
مسار حقيقي بعد الآن**.

**لا Claude، مجاني فقط (قرار صريح من المالك، نفس اليوم):** "احذف كلود
لانه ليس مجاني، اترك المجاني و بس". مزوّد الاستدلال الوحيد المتبقي الآن
Groq (أساسي) مع Gemini احتياطياً - كلاهما مجاني بالكامل. **البحث في
الويب لدراسة المنافسين معطَّل الآن بالكامل** (`MockWebSearchTool` دائماً)
لأن التنفيذ الحقيقي الوحيد المتوفر لهذه الميزة كان يعتمد على Claude حصراً
ولا بديل مجاني له في المشروع بعد - مقايضة حقيقية، لا حلاً معادلاً.
التفاصيل الكاملة والأرقام الحقيقية في `docs/SOURCES.md` "Down to one
agent" و"No agent gate at all, and no Claude".

## التشغيل المتواصل الحقيقي - مجاناً بالكامل، بلا خادم وبلا بطاقة بنكية

**المشكلة التي تحلّها هذه الطريقة**: لا تملك خادماً دائماً، ولا تريد شراء
واحد أو تسجيل بطاقة بنكية في أي خدمة جديدة. تشغيل البرنامج مباشرة من
داخل محادثة Claude مرفوض عمداً من نظام الأمان الخاص بـ Claude Code نفسه
("Real-World Transactions") - هذا حاجز أمان مقصود، ليس عطلاً، ولا يمكن
تجاوزه ولا ينبغي.

**الحل الحقيقي: GitHub Actions.** مستودعك عام (Public)، وهذا يعني
**دقائق تشغيل مجانية غير محدودة من GitHub نفسها** - بلا بطاقة، بلا حساب
جديد (تستخدم حسابك الحالي على GitHub). الملف `.github/workflows/run_hourly.yml`
يُشغّل المشروع فعلياً كل 10 دقائق، تلقائياً، للأبد، طالما المستودع موجوداً
على GitHub - بلا أي علاقة بهذه المحادثة أو بأي جلسة Claude.

**الخطوة الوحيدة المتبقية عليك (لا بديل عنها، لا علاقة لها بالدفع):**
1. افتح صفحة المستودع على GitHub من المتصفح.
2. **Settings** (أعلى الصفحة) ← **Secrets and variables** ← **Actions**.
3. اضغط **New repository secret** لكل مفتاح من مفاتيحك الحقيقية وضَع قيمته
   (نفس القيم الموجودة في `.env` عندك): `GROQ_API_KEY`، `GEMINI_API_KEY`،
   `SHOPIFY_SHOP_URL`، `SHOPIFY_CLIENT_ID`، `SHOPIFY_CLIENT_SECRET`،
   `CJ_API_KEY`، `TELEGRAM_BOT_TOKEN`، `TELEGRAM_CHAT_ID`، وأضف أيضاً
   `DRY_RUN` بالقيمة `false`.
4. بمجرد إضافتها، سيبدأ التشغيل تلقائياً خلال 10 دقائق على الأكثر - أو
   اذهب لتبويب **Actions** في المستودع واضغط **Run workflow** لتشغيله
   فوراً يدوياً والتأكد.
5. لمراقبة ما يحدث فعلياً: نفس تبويب **Actions**، اضغط على أي تشغيل
   لرؤية السجلات الحقيقية.

التفاصيل الكاملة (ولماذا بُني هكذا تحديداً) في `docs/SOURCES.md`
"GitHub Actions real run".

المشروع يعمل افتراضياً بوضع `DRY_RUN=true`: لا شراء حقيقي، لا نشر حقيقي، لا
رسائل حقيقية للزبائن — كل شيء يُسجَّل فقط في قاعدة بيانات SQLite محلية
(`nexus_commerce.db`) مع سجل تدقيق كامل لكل قرار.

## خطوات الإعداد بالترتيب

### 1. المتطلبات

- Python 3.12 (أو Docker، القسم أدناه).
- حساب Shopify له Access Token من نوع Admin API.
- حساب CJ Dropshipping (المفاتيح تُحفظ، لكن التنفيذ الحقيقي ضدها غير جاهز بعد
  — انظر "ما ينقص" في `docs/UNVERIFIED.md` وفي التقرير النهائي).
- بوت Telegram (عبر [@BotFather](https://t.me/BotFather)) — هذا الجزء جاهز
  ويعمل حقيقياً بدون أي نقص.
- مفتاح Anthropic API (`ANTHROPIC_API_KEY`) — هذا ما يفكر به الوكلاء الخمسة
  فعلياً، وهو الجزء الوحيد الذي **يستدعي API خارجياً حقيقياً حتى في DRY_RUN**،
  لأن اتخاذ القرار نفسه ليس من "الأفعال ذات الأثر الخارجي" التي يوقفها DRY_RUN.

### 2. التثبيت المحلي (بدون Docker)

```bash
cd nexus-commerce
python3.12 -m venv .venv
.venv/bin/pip install -r requirements.txt
cp .env.example .env
```

افتح `.env` وعبّئ ما تملكه من مفاتيح (اتركه فارغاً لأي خدمة لا تملك مفتاحها
الآن — المشروع يستخدم نسخة محاكاة (mock) تلقائياً لتلك الخدمة بدل أن يفشل).

### 3. الحصول على TELEGRAM_CHAT_ID

1. أنشئ بوتاً عبر `@BotFather` واحصل على `TELEGRAM_BOT_TOKEN`.
2. أرسل أي رسالة للبوت من حسابك أنت (يجب أن تبدأ المحادثة أنت أولاً).
3. افتح `https://api.telegram.org/bot<TOKEN>/getUpdates` في المتصفح وابحث عن
   `"chat":{"id": ...}` — هذا هو `TELEGRAM_CHAT_ID`.

### 4. تشغيل الاختبارات (يجب أن تنجح كلها قبل أي شيء آخر)

```bash
.venv/bin/python -m pytest -v
```

النتيجة الفعلية الحالية لهذا التشغيل: **68 اختباراً، كلها ناجحة (68 passed)**
— التفاصيل الكاملة والأرقام في `docs/FINAL_REPORT.md`.

### 5. التشغيل محلياً

```bash
.venv/bin/python -m src.main
```

- إن كان `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID` مضبوطين: يبدأ الاستماع
  الحقيقي لأزرار "موافق"/"رفض" على Telegram فوراً.
- إن لم يكونا مضبوطين: المقترحات التي تصل لمرحلة الإجماع تبقى بحالة
  `awaiting_telegram` منتظرة إلى أن تضبط المفتاحين.
- الحلقة الرئيسية (APScheduler) تعمل في الخلفية: كل خطوات المشروع (الطلبات
  المدفوعة ← التتبع ← مراجعة الأسعار، واقتراح منتجات جديدة) تعمل على نفس
  الفترة `HOURLY_INTERVAL_MINUTES` — بطلب صريح من المالك. تنبيه: اقتراح
  المنتجات الجديدة يستدعي بحث CJ حقيقي وإجماع الوكلاء الخمسة كاملاً لكل
  مرشّح، فعلى فترة دقيقة واحدة سيستهلك حصة مزوّد الذكاء الاصطناعي المجاني
  بسرعة (راجع `docs/UNVERIFIED.md` "Gemini free tier reliability").

### 6. التشغيل عبر Docker (للسيرفر)

```bash
docker compose up -d --build
```

يقرأ `docker-compose.yml` ملف `.env` تلقائياً، ويحفظ قاعدة البيانات في جزء
(volume) دائم باسم `nexus_commerce_data` حتى لا تُفقد بين عمليات إعادة
التشغيل.

## كيف تنتقل من DRY_RUN إلى التشغيل الحقيقي

**هذا القسم الأهم قبل أي صرف حقيقي.** اقرأه كاملاً قبل تغيير `DRY_RUN`.

### أولاً: ما هو جاهز للتشغيل الحقيقي الآن

**كل شيء جاهز، كوداً ومفاتيح.** لا يوجد أي `NotImplementedError` متبقٍ في
`RealShopifyClient` أو `RealCJClient` — كل استعلام وmutation حقيقي، مبني
على توثيق Shopify وCJ الرسمي (التفاصيل والمصادر في `docs/SOURCES.md`).

- **Anthropic (تفكير الوكلاء الخمسة)**: حقيقي.
- **Telegram (موافقتك/رفضك)**: حقيقي.
- **Shopify**: حقيقي — نشر منتج، قراءة الطلبات وحالة الدفع، تعديل سعر،
  تحديث تتبع. المصادقة عبر **Client credentials grant** (`SHOPIFY_CLIENT_ID`
  + `SHOPIFY_CLIENT_SECRET` — يُنشئهما الكود نفسه توكن وصول تلقائياً، بلا
  أي خطوة تثبيت يدوية أو OAuth).
- **CJ Dropshipping**: حقيقي — بحث، تفاصيل منتج، تكلفة شحن، **طلب فعلي من
  المورّد**، تتبع شحنة.

بضعة حقول صغيرة موثّقة صراحة كافتراضات غير مؤكدة 100% (لا كحقائق) — راجع
`docs/UNVERIFIED.md` قبل أول طلب حقيقي؛ الأبرز: `shippingProvince` (محافظة
عنوان الشحن) لا مصدر لها حالياً في بيانات Shopify التي يقرؤها المشروع،
فطلب لوجهة تتطلب محافظة سيرجع خطأً واضحاً من CJ بدل بيانات خاطئة بصمت.

### ثانياً: من أين تأتي كل مفاتيحك (إن أنشأت مشروعاً جديداً من الصفر)

- **`SHOPIFY_CLIENT_ID` و`SHOPIFY_CLIENT_SECRET`**: من `dev.shopify.com` →
  تطبيقك → **App settings** → قسم **"Credenziali"/Credentials** — ظاهران
  مباشرة بلا أي تثبيت أو موافقة تاجر (لأن هذا تطبيق يعمل على متجرك أنت
  فقط). لا حاجة لأي توكن `shpat_...` يدوي.
- **`CJ_API_KEY`**: من حسابك على `cjdropshipping.com` → ثبّت تطبيق "API" من
  App Store الخاص بـ CJ → صفحة "Get API Key" → Add API → Type: API Key →
  انسخ المفتاح.

### ثالثاً: خطوات الانتقال الفعلية، بالترتيب

1. **عبّئ كل المفاتيح في `.env`**: `ANTHROPIC_API_KEY`، `SHOPIFY_SHOP_URL`،
   `SHOPIFY_CLIENT_ID`، `SHOPIFY_CLIENT_SECRET`، `CJ_API_KEY`
   (`CJ_API_BASE_URL` له قيمة افتراضية صحيحة بالفعل)، `TELEGRAM_BOT_TOKEN`،
   `TELEGRAM_CHAT_ID`.
2. **اطّلع على `MIN_MARGIN`** — تذكير: منذ 2026-10-14 بتعليمات صاحب المشروع
   لم يعد سقفًا للرفض التلقائي (لا يوجد `MAX_ORDER_COST`/`DAILY_SPEND_LIMIT`
   أصلاً، ولا حد أدنى ثابت للهامش) — الفحص الوحيد قبل وصول المقترح للوكلاء هو
   "هل الربح الحقيقي أكبر من صفر؟". راجع `src/tools/limits.py`.
3. **شغّل الاختبارات كاملة** (`pytest -v`) — يجب أن تبقى كلها ناجحة.
4. **اختبر بـ `DRY_RUN=true` أولاً** ضد حسابك الحقيقي (Shopify/CJ حقيقيان،
   لكن بلا تنفيذ فعلي) وراقب سجل التدقيق (`audit_log` في قاعدة البيانات)
   وتأكد أن القراءات (الطلبات، الأسعار) صحيحة.
5. **فقط بعد كل ما سبق**: غيّر `DRY_RUN=false` في `.env` وأعد تشغيل الخدمة.
   من هذه اللحظة، أي مقترح يصل لإجماع الوكلاء **يُنفَّذ تلقائيًا وفورًا، بلا
   أي موافقة بشرية**: نشر منتج حقيقي، تغيير سعر حقيقي، طلب حقيقي من CJ بأموال
   حقيقية. تيليغرام يُرسل إشعارًا فقط بعد إتمام بيع حقيقي (CJ_ORDER ناجح).

### رابعاً: احتياطات لا يجب تجاوزها أبداً

- طلب المنتج من CJ لا يحدث إلا بعد أن يكون `financial_status` للطلب في
  Shopify هو `paid` بالفعل — هذا مفروض في الكود نفسه
  (`src/tools/limits.py::check_payment_confirmed`)، وليس مجرد اتفاق شفهي.
- لا يوجد سقف إنفاق على طلب CJ (قرار صاحب المشروع 2026-10-14، "ليس هناك سقف
  الانفاق مادام الزبون هو من يدفع") — آمن لأن كل مقترح CJ_ORDER مبني أصلاً
  على طلب Shopify مدفوع فعلاً، فالمبلغ مال الزبون لا مال المتجر.
- لا تحذف أو تُقلّل سجل `audit_log` — هو الدليل الوحيد القابل للمراجعة على كل
  قرار اتُّخذ ومن وافق عليه ومتى.

## هيكل المشروع (مرجع سريع)

```
src/
  agents/        وكيل واحد (A1..A5)، بروتوكول الإجماع، مراجعة ما بعد التنفيذ
  db/            المخطط، الموديلات، كل استعلامات SQL
  integrations/  Anthropic / Shopify / CJ / Telegram — كل واحدة: واجهة + حقيقية + mock
  tools/         حاسبة الربح، حدود الصرف، أداة بحث الويب
  workflows/     الأنابيب الأربعة (طلبات/تتبع/أسعار/منتجات جديدة) + منفّذ + pipeline عام
  app.py         نقطة اختيار حقيقي-أو-mock لكل خدمة بحسب ما هو مضبوط في .env
  scheduler.py   وظائف APScheduler الساعية واليومية
  main.py        نقطة التشغيل الدائمة (الخدمة)
tests/           126 اختباراً، منها محاكاة end-to-end كاملة بوضع DRY_RUN
                 واختبارات Shopify/CJ الحقيقيين (الشبكة فقط محاكاة)
docs/
  SOURCES.md     كل مصدر توثيق رسمي استُخدم فعلياً، مع الرابط
  UNVERIFIED.md  كل ما لم يُتحقَّق منه ولم يُستخدم
  FINAL_REPORT.md التقرير النهائي: ماذا بُني، نتائج الاختبارات الفعلية، الناقص
```
